# 4. Use Navigation 3 (Compose Multiplatform)

Date: ${SCAFFOLD_DATE}
Status: Accepted

## Context

We need a navigation library that works across all Compose Multiplatform targets (Android, iOS, desktop, web), supports type-safe destinations, and aligns with where the JetBrains + AndroidX stack is heading.

Alternatives considered:
- **AndroidX Navigation Compose 2.x** with `@Serializable` + `toRoute<T>()` — stable, well-documented, KMP support added later. Different mental model from Nav 3.
- **Voyager (adrielcafe/voyager)** — Compose-first KMP nav with ScreenModel integration. Smaller community; less aligned with JetBrains' future direction.
- **Decompose (arkivanov/decompose)** — lifecycle-aware components with state preservation. Steeper learning curve; more architectural.

## Decision

Use [Navigation 3](https://kotlinlang.org/docs/multiplatform/compose-navigation-3.html) (`androidx.navigation3:navigation3-ui:1.1.2`). Routes are `@Serializable` data classes/objects implementing `NavKey`. Back stack is a user-owned `SnapshotStateList<NavKey>` constructed via `rememberNavBackStack(RootRoute)` and rendered with `NavDisplay`.

The nav graph is composed via the `entryProvider { }` DSL: each feature exposes a public `EntryProviderBuilder<NavKey>.addFooEntries(...)` extension that contributes `entry<FooRoute> { FooScreen(...) }`, and `:composeApp` calls those inside `NavDisplay(entryProvider = entryProvider { addFooEntries(...) })`. The app never references a feature's `Screen` directly — that keeps `FooScreen`/`FooViewModel`/`FooState` `internal` to their feature module. Cross-feature navigation is passed in as callbacks (the app owns the back stack and all target routes), so a feature never imports another feature's Route.

## Consequences

- Easier: full KMP support; aligned with JetBrains' current direction; user-owned back stack is more flexible than Nav 2's auto-managed graph; adaptive layouts come naturally; per-feature entry contributions keep screens encapsulated and the app's nav wiring declarative.
- Harder: new API surface, fewer Stack Overflow answers than Nav 2; polymorphic serialization config needed for nav state save/restore.
- Reviewer enforces: every route is `@Serializable` and implements `NavKey`; the app composes features via `addFooEntries(...)` in `entryProvider { }`, not a `when` referencing screens; a feature never imports another feature's Route; navigation is driven by a consumable `pendingNavigation: Route?` state slot set inside `intent {}`, with the back stack mutated in the Composable via `LaunchedEffect` observing that slot — never `postSideEffect` (effect type is `Nothing`), never side-effected from outside.
